Design proposal · v0.1 · 23 Sep 2026

Relay.

A harness that takes BA stories all the way to reviewed, merged code. It works with any language or stack, and it lets a small team of people and their AI agents build one feature together without stepping on each other.

Draft for discussionName: placeholder, see Q1Reads in: about 20 minutes

01In one minute

  • WhatA set of skills (slash commands) plus one shared folder. Together they turn stories into requirements, a design, small tasks, code and reviewed PRs.
  • Any stackThe skills never assume a language. Relay reads each repo once, writes down how that repo builds, tests and is structured, and follows those rules.
  • MemoryEvery step writes plain markdown into _relay/features/<feature>/. The code repo ignores this folder, but the folder is its own small git repo, so the whole team shares it.
  • TeamTasks are cut so people can work in parallel: contracts first, then independent slices. Every finished task leaves a changelog with heads-up notes that the next agent reads before it writes code.
  • ControlPeople approve at four gates. Agents never merge to develop, never resolve merge conflicts and never write to production.
  • One command/relay next checks where the feature is and offers the next step, so nobody has to remember every command.

02Why we need this

AI works well for one person in one chat. In a team it breaks in small, annoying ways:

  • Every agent starts from zero. My agent does not know what my teammate's agent changed an hour ago.
  • Specs live in chat history. When a story changes, nobody knows which parts of the design or the code are now wrong.
  • Status lives in people's heads, or in a board that nobody updates.
  • Every project is different. Java here, Node there, Bitbucket for one client, GitHub for another. Prompts written for one project do not carry over.

Relay fixes this with one idea: every step leaves a file behind, and those files are the team's shared memory. Agents read them before they act and write to them after.

03Goals and non-goals

Goals

  • Works for any language, framework and stack.
  • Works with GitHub, Bitbucket, GitLab and Azure DevOps. Works with Jira, other trackers, or no tracker.
  • A small team can split one feature and work in parallel.
  • Every step can be run again. It updates what is there; it does not start over.
  • People decide. Agents do the heavy lifting.

Not goals

  • Replacing the BA or Jira. Stories still come from the BA.
  • Merging anything into develop by itself.
  • Resolving merge conflicts by itself.
  • Changing production systems, ever.

04The whole flow

A feature (usually one epic) moves through eight stages. Each stage is one skill. Each skill reads what the earlier stages wrote and adds its own files.

Stage and gate status

Each feature has one small file, feature.yaml, that says which stage it is in and who approved each gate. Anyone can run /relay status to see it.

feature: PAY-120-refund-flow
epic: PAY-120
stage: building     # requirements | design | tasks | checked | building | feature-review | done
gates:
  requirements: { approved_by: ba-lead,   at: 2026-09-18 }
  design:       { approved_by: tech-lead, at: 2026-09-20 }
  tasks:        { approved_by: tech-lead, at: 2026-09-21 }
  ship:         null
feature_branch: feature/PAY-120-refund-flow
repos: [payments-api, payments-web]
One command to start with

/relay next reads feature.yaml and the task files, then says what should happen next and offers to run it. For example: "Design is approved. Next: cut tasks with /relay plan. Run it now?" or "T05 is ready and nobody owns it. Build it?" New people only need to learn this one command.

05What I changed from your idea, and why

Most of your idea stays as it is. These are the places where I think a different approach works better. Each one is open for discussion.

06Staying stack agnostic

Relay has three layers. Only the bottom two know anything about your tools, and both are either learned or picked in config. The skills themselves never name a language.

How Relay learns a repo

/relay learn runs once per repo (and again when things change). It:

  1. Reads build and CI files it finds: package.json, pom.xml, build.gradle, go.mod, *.csproj, pyproject.toml, Makefile, pipeline files.
  2. Reads the README and the folder layout.
  3. Runs the build and the tests once, to prove the commands work.
  4. Picks two or three exemplar files for each kind of thing (an endpoint, a test, a migration, a UI component). These show the house style better than any rule list.
  5. Writes profile.md and asks you to fix anything wrong.
# payments-api
Stack:   Java 21, Spring Boot 3, PostgreSQL, Flyway
Build:   ./gradlew build
Test:    ./gradlew test        (one class: ./gradlew test --tests <Class>)
Lint:    ./gradlew spotlessCheck
Layout:  api/ (controllers) · domain/ (logic) · infra/ (db, clients)

## Exemplars
endpoint:  src/main/java/.../payments/PaymentController.java
test:      src/test/java/.../payments/PaymentControllerTest.java
migration: src/main/resources/db/migration/V42__add_payment_index.sql

## House rules
- Controllers call services, never repositories.
- Money is BigDecimal, never double.
- Every endpoint has an integration test with Testcontainers.

Setup: config and secrets

/relay init asks a few questions (platform, tracker, spec repo URL) and writes relay.yaml. Secrets never go in files. They come from environment variables, and init checks they are set.

Where an MCP server exists (for example the Atlassian one), the adapter uses it. Where it does not, the adapter falls back to a CLI (gh) or plain REST calls. Either way the skill sees the same small set of actions: get story, create sub-task, get PR diff, post inline comment.

Running a skill again

Every skill is safe to run twice. By default it updates: it reads the current file, changes only what needs to change, and lists what it changed. Pass --fresh to rewrite from scratch. The old version is still in the spec repo's git history.

Anything a person writes between these markers is never touched by a skill:

<!-- keep -->
Dev note: orders before 2024 have no payment date. Handle null.
<!-- /keep -->

Deleting a feature

/relay drop PAY-120 lists every file it will delete, asks you to confirm, deletes the folder and pushes. Because the spec repo is git, a dropped feature can still be brought back. It does not touch Jira tickets or branches unless you pass --with-branches or --with-tickets, and even then it asks again.

08Sharing with the team

This is the hardest part of your idea. The folder must be shared, because Dev B needs to see what Dev A did. But it must not go into the code repo, and many people update it at the same time. Here are the options:

OptionGoodBad
Commit into the code repoSimple. Lives next to the code.Noise in every PR. Status changes cause conflicts on feature branches. You did not want this.
Separate spec repo pickFull history and undo. Works offline. One spec repo can cover a feature that spans many code repos.One more repo. Needs the rules below to avoid conflicts.
Tracker only (Jira holds everything)Leads already look there.Jira is bad at long markdown, diagrams and changelogs. Agents read files far better than tickets.
Shared drive folderNo git knowledge needed.No real conflict handling. Silent overwrites. No history.

Rules that prevent conflicts

  1. One writer per file. The planner writes task.md. Only the task's owner writes its status.yaml and changelog.md. Two people almost never touch the same file.
  2. Nothing summed up is stored. The board, the sheet and the feature's progress are computed from the task files each time. There is no shared STATUS.md to fight over.
  3. Small commits, pushed right away. Every skill starts with git pull --rebase and ends with commit and push. Commit messages look like relay(PAY-120): T03 in-review.
  4. Claiming a task is a commit. If two people claim T05 at once, the second push fails. The skill pulls, sees T05 already has an owner, and stops. Git gives us a free lock.

How status updates when a PR is merged

Default: on the next sync

Every skill starts with a sync. The sync asks the git platform which task PRs are merged and marks those tasks done. Task branches carry the task ID in their name, so matching is exact. No CI setup needed.

Optional: right away, from CI

A small pipeline step in the code repo runs when a PR into a feature branch merges. It reads the task ID from the branch name and pushes done to the spec repo. Relay ships ready-made pipeline files for GitHub Actions and Bitbucket Pipelines.

10Requirements and grooming notes

/relay intake PAY-120

Pulls the epic and every story under it. It writes one overview file and one file per story. Every acceptance criterion gets a stable ID so the rest of the flow can point at it.

When you run it again, it compares the new stories with the saved ones. Changed stories get marked, and it lists what they affect downstream: "PAY-121.AC2 changed. Design §4.2 and tasks T03 and T05 point at it." Use --story PAY-121 to refresh one story, or --fresh to rebuild everything.

---

<!-- keep -->
Dev note: orders before 2024 have no payment date.
<!-- /keep -->

/relay context grooming.vtt --story PAY-121

Give it a call transcript, meeting notes, an email thread or a screenshot. It saves the raw file untouched in context/raw/, then writes a clean note file with decisions, answers and new questions. Each point links to a story or AC and carries a timestamp or quote, so anyone can check the source.

Rule

The story is the contract. Call notes add detail. If a note conflicts with the story, Relay does not pick one. It adds a question to questions.md for the BA.

11Design and the review page

/relay design

Reads the requirements, the context notes, the profile, and the real code the feature will touch. Then writes design.md with these parts:

  • Summary and what is in and out of scope.
  • What exists today, with file paths. Every claim about the code points to a file.
  • Proposed design: components, data model, API and event contracts, sequence diagrams (Mermaid).
  • AC map: a table showing which design section covers each AC.
  • Risks, rollout (flags, migrations, backfills) and open questions.
  • Decisions as short ADR files, so the "why" survives.

The review page

Reading a long design in chat and then typing "in the part about refunds, the second paragraph..." is slow and loses context. So design also builds design.html: one self-contained page that renders the markdown and the Mermaid diagrams. Reviewers comment right on it.

How it works:

  • Select any text, a table row, or a whole diagram (or one node in it) and write a comment. Comments are saved in the browser, so closing the tab loses nothing.
  • When the page is built, every block remembers which lines of design.md it came from. So each comment knows its exact source lines, even after edits.
  • Copy feedback puts one block on the clipboard. Paste it in chat. The agent goes through each comment, changes the design or answers the question, and says which it did.

12Small, independent tasks

Parallel work only happens if tasks do not wait on each other. /relay plan always cuts tasks in the same shape:

Rules the planner follows

  • One task, one PR, one day or less. Sizes are S (half a day) or M (one day). Anything bigger is split.
  • Wave 0 is contracts only: API schemas, shared types, DB migrations, interfaces with stub code. Small and fast, so others are unblocked quickly.
  • Each task lists the files it will touch. Two tasks in the same wave may not touch the same files. The checker enforces this.
  • Each task says what it gives to others and what it must not change.
  • Every task covers at least one AC, and every AC is covered by at least one task with a named test.
---
id: T03
title: Refund API endpoint
wave: 1
stories: [PAY-121]
covers: [PAY-121.AC1, PAY-121.AC2]
depends_on: [T01]
repo: payments-api
touches: [src/**/refunds/api/**, src/**/refunds/RefundService.*]
size: M
---
## Goal
Customers can ask for a full or partial refund with POST /refunds.

## Read first
- design.md §4.2 Refund API, §5 Error codes
- T01 changelog (the RefundRequest contract)

## Gives to others
- RefundService.request(orderId, amount), used by T05 and T07.

## Must not change
- The RefundRequest / RefundStatus contract from T01. If you must,
  write it under "Heads-up" in your changelog.

## Done when
- [ ] AC1: refund refused after 30 days     → test: refuses_refund_after_30_days
- [ ] AC2: partial refund of 1.00 accepted  → test: accepts_partial_refund

/relay check

A second agent, with fresh eyes, reads the stories, the design and the tasks and builds a coverage table. It looks for gaps (an AC with no task, a task with no test), overlaps (two tasks, same files, same wave), loops in dependencies, and tasks that are too big. The tasks gate cannot pass while there are gaps.

13Building a task

/relay build T05 is where most of the time goes. The steps run in this order:

  1. Sync. Pull the spec repo and mark any merged PRs as done.
  2. Claim. Set the task to in-progress with your name and push. If someone else already owns it, stop.
  3. Check it is ready. Are the tasks it depends on merged? If not, say which ones and stop, unless you ask it to work against the contract with stubs.
  4. Learn. Read profile.md, learnings.md and the exemplar files. Then read the real code the task touches.
  5. Catch up. Read the changelog of every done task in this feature, Heads-up and Different from the design notes first. Read the design changelog. If a story this task covers has changed since the task was written, stop and flag it.
  6. Branch. Create the task branch from the latest feature branch.
  7. Build. Write the tests from "Done when" first where it fits, then the code, in the house style.
  8. Verify. Run build, lint and tests with the profile commands. Fix until green.
  9. Record. Write changelog.md: what changed, heads-up for others, and anything different from the design.
  10. Hand off. Push, open a PR into the feature branch, set status to in-review and save the PR link.

The changelog is short and has fixed parts, so agents can find what matters fast:

## 2026-09-22 · T01 API contracts · PR #398 merged

### What changed
- Added RefundRequest and RefundStatus in src/**/refunds/contract/.
- Added the refund.completed event schema.

### Heads-up for other tasks
- RefundStatus has a new value PARTIAL (not in the design). T05 must show it.
- Amounts are in minor units (cents, long), not decimals.

### Different from the design
- Design §4.1 said decimal amounts. Changed to minor units after a talk
  with the tech lead. Design changelog entry D-4 added.

14Branches and staying fresh

Task PRs cannot go straight to develop, because half a feature would break things. So each feature gets a feature branch (your "mother branch"). Every task gets its own branch from it, and its PR goes back into it. Only when the whole feature is done and reviewed does one PR go from the feature branch into develop.

  • Task branch names carry the task ID (feature/PAY-120/T03-refund-api). That is how sync matches PRs to tasks.
  • We merge develop into the feature branch. We never rebase it, because rebasing a shared branch breaks everyone's task branches.
  • When build starts, it merges the latest feature branch into the task branch, so tasks pick up the freshen too.

/relay freshen: keep the feature branch up to date

Other teams keep merging into develop. If the feature branch falls days behind, the final merge hurts. When you create the feature branch, /relay branch asks: "Do you want develop merged into this branch every weekday at 06:00?" This is optional.

Where it runsGoodWatch out
CI scheduled pipeline pickRuns even when laptops are off. Uses the team's normal CI.Needs a bot user that can push to feature branches.
Claude Code scheduled routineNo pipeline to write. Can explain conflicts in plain words.Uses AI credits for what is mostly a script.

The merge itself is a plain script. AI is only used to write the report when something goes wrong, for example: "Conflict in RefundService.java: develop renamed calculateFee, T03 added a call to the old name."

15PR review

/relay review 412 works for any language because it does not bring its own rule book. It judges the PR against things this project already has:

  1. The task and its ACs. Does the PR do what the task says? Is every AC tested?
  2. The design and contracts. Does it match? If not, is the difference written in the changelog?
  3. The house style. profile.md, learnings.md and the exemplar files.
  4. General quality. Bugs, security, error handling, missing tests.

It posts inline comments on the exact lines, each marked must fix should fix or nit, plus one summary comment. It never approves or merges; that stays with people. A copy of the review is saved in reviews/PR-412.md.

Without a PR, /relay review --path src/refunds reviews existing code and writes the findings to a file.

16Jira sub-tasks and the lead's sheet

There are two audiences. Agents read the markdown in _relay/. People, and leads most of all, look at Jira or a spreadsheet. /relay publish keeps the two in step.

With Jira

  • Creates one sub-task per task under the story it mainly covers, and links any other stories.
  • The sub-task holds a short summary and a pointer to the task file.
  • The Jira key is saved in status.yaml, so running it again updates instead of duplicating.
  • The lead assigns people in Jira. The next sync copies the assignee into the task's owner.
  • Status changes move the Jira ticket too (the mapping lives in relay.yaml).

Without Jira

  • --to csv or --to xlsx exports every task to a sheet the lead can open or import into Google Sheets.
  • The lead fills in the Owner column. /relay publish --import sheet.csv reads the owners back.
  • With a Google Drive connection, it updates the Google Sheet in place.

17Diagnose and fix bugs

/relay diagnose PAY-310 --allow logs,k8s:staging,db:readonly works the way a careful developer does. The skill teaches the method, not the tools, so it fits any stack:

  1. Read the bug. Steps, expected vs actual result, environment, time it happened.
  2. Gather facts. Logs, recent deploys, the code on that path, the data involved. Read only.
  3. List guesses, most likely first, each with a cheap way to test it.
  4. Test one guess at a time and write down what each test showed.
  5. Reproduce with a failing unit test, or a small script if a unit test is not possible.
  6. Fix the smallest thing that makes that test pass.
  7. Check wider. Run the full test suite. Look for the same bug pattern elsewhere.
  8. Write it up in bugs/PAY-310/rca.md: root cause, fix, how to stop it happening again.

Three layers of safety

A written rule in a skill is the weakest guard, because a model can get it wrong. So Relay stacks three:

LayerWhat it isStrength
CredentialsA read-only DB user. A view-only Kubernetes role. init asks for these and warns if the given access can write.cannot be bypassed
Guard hookA hook that runs before every shell command, checks it against safety.yaml, and blocks matches. Works even if the model is wrong.strong
Skill rulesPrefer staging. Always LIMIT. Mask secrets. Name the production context out loud before touching it, every session.helpful, not enough alone
 
# read by the guard hook before every shell command
block:
  - 'kubectl\s+(delete|apply|edit|patch|scale|replace|drain|cordon)'
  - 'kubectl\s+rollout\s+(restart|undo)'
  - '\b(DROP|TRUNCATE|ALTER|GRANT)\b'
  - '\bDELETE\s+FROM\b'
  - '\bUPDATE\s+\w+\s+SET\b'
  - 'git\s+push\s+.*(--force|-f)\b'
ask:
  - 'kubectl\s+(exec|port-forward)'
  - '--context[= ]\S*prod'

18One communication style

You asked if it is even possible. Yes, mostly. Tone can be steered very well, but not guaranteed. Simple rules (banned words, no em-dashes, max sentence length) can be enforced.

  • One file, _relay/style.md, holds the rules.
  • Every skill's first step is "read style.md". It is also imported from the repo's CLAUDE.md, so normal chat follows it too.
  • Templates (story, design, task, changelog) carry the structure, so documents look the same no matter who made them.
  • A small lint hook checks files written by Relay for the mechanical rules and asks the agent to fix them before it finishes.
# How we write

- Simple English. Short sentences. One idea per sentence.
- Lead with the answer, then the reason.
- Use the BA's words for business things and the code's words for code things.
  Same word every time.
- Tables for comparisons. Diagrams for flows. Lists for steps.
- No em-dashes. Avoid: leverage, robust, seamless, utilize.
- In chat: what I did, what I found, what I need from you.
- In design docs: every claim about the code points to a file path.

19How we package it

Relay ships as a Claude Code plugin: skills, helper agents, hooks and scripts in one versioned repo. Teams install it once. The skills are plain markdown, so other agents that read skill files can use them too.

relay/                           the plugin, its own repo
├── .claude-plugin/plugin.json
├── skills/
│   ├── intake/SKILL.md          + templates/story.md
│   ├── design/SKILL.md          + templates/design.md, review-page.html
│   ├── plan/  check/  build/  review/  ship/
│   ├── freshen/  diagnose/  publish/  context/
│   └── next/SKILL.md
├── agents/                      focused helpers: planner, checker, reviewer
├── hooks/hooks.json             safety guard, style lint, auto sync
├── scripts/                     git + platform plumbing, no AI
│   ├── freshen.sh
│   ├── platform/  github  bitbucket  gitlab  azure
│   └── tracker/   jira  csv  xlsx
└── ci/                          ready pipelines: freshen, mark-done

A simple rule decides what goes where: if a step needs judgment, it is a skill. If it is always the same, it is a script. Scripts are cheaper, faster and give the same result every time.

21Open questions

These need a decision from us before Phase 1 starts. My suggestion is in brackets.

  1. Name. Is "Relay" with a _relay/ folder OK? (The baton idea fits: each task hands its changelog to the next.)
  2. Spec repo scope. One per team, or one per product? (One per team. Features list the code repos they touch.)
  3. Source of truth for status. Spec repo first with Jira mirrored, or Jira first? (Spec repo first. Agents need files; Jira is the window for people.)
  4. Who approves each gate? (BA for requirements, tech lead for design and tasks, tech lead plus one dev for ship.)
  5. Merge or rebase when freshening? (Merge, because the feature branch is shared.)
  6. Confluence. Should the approved design also be pushed to Confluence for the BA? (Yes, read-only, as a later adapter.)
  7. Tests in freshen. They cost CI minutes but catch breaks early. (Run them. It is once a day.)
  8. A story changes after build started. Create change tasks by itself, or stop and ask? (Stop and ask. Show the impact list first.)
